# 일일 학습 브리핑 양식

부트캠프에서 당일 다룬 개발 지식을 빠르게 복습하고, 흩어진 개념을 하나의 흐름으로 연결하며, 실제 문제에 맞는 기술을 선택하는 판단력을 기르기 위한 양식이다.

## 작성 원칙

- 전체 분량은 5분 안에 읽을 수 있게 제한한다.
- `대화에서 다룸`, `직접 설명함`, `맥락에 맞게 판단함`을 구분한다.
- 상단의 항목 목록은 학습 범위를 보여주는 색인으로 사용한다. 본문에는 설명에 필요한 개념명만 다시 쓴다.
- 당일 배우거나 비교한 핵심 개념은 정식 기술 용어를 빠짐없이 노출한다. 핵심 개념은 나중에 독립적으로 떠올리거나 검색해야 하는 패턴·아키텍처·프레임워크 기능·비교 축을 뜻한다.
- `아키텍처`, `MSA 지향 구조` 같은 상위 범주로 `오케스트레이션(Orchestration)`, `코레오그래피(Choreography)`, `사가 패턴(Saga Pattern)` 같은 구체적인 개념명을 대신하지 않는다.
- 한국어와 영어 용어가 함께 쓰이는 개념은 첫 등장에 병기하고, 코드 식별자와 어노테이션 이름은 정확히 쓴다.
- 사례로만 설명한 개념도 본문에서 그 사례가 어떤 정식 개념에 해당하는지 명시한다. 독자가 사례만 보고 개념명을 추론하게 두지 않는다.
- 당일 가장 중요한 개념 3~6개를 하나의 중심 흐름이나 맥락으로 연결한다.
- 관련성이 약한 개념을 억지로 하나의 흐름에 포함하지 않는다.
- 기술의 정의보다 어떤 문제를 해결하고, 무엇은 해결하지 못하며, 어떤 조건에서 선택이 달라지는지를 설명한다.
- 판단 사례는 실제 코드나 당일 질문에서 하나만 고른다. 선택 문제가 없으면 생략한다.
- 특정 Entity와 업무 규칙은 판단 맥락을 설명하는 데 필요한 만큼만 사용한다.
- 메타인지는 질문 횟수나 인상으로 추정하지 않고, 브리핑 전에 받은 직접 설명과 판단을 근거로 작성한다.
- 근거가 없는 이해 수준과 이전 대비 변화는 `미확인`으로 표시한다.
- 아키텍처 흐름은 Mermaid가 아닌 Markdown 텍스트 도식으로 표현한다.
- 상세 원리와 예외는 추가 질문이 들어오면 확장한다.

## 브리핑 전 확인

학습이 끝난 뒤 사용자가 오늘자 학습 브리핑 생성을 요청했을 때만, 브리핑을 보여주기 전에 당일의 중심 개념을 묻는 통합 질문 하나를 먼저 제시한다. 학습 내용을 기록하는 단계에서는 일일 브리핑 파일을 만들거나 질문을 먼저 건네지 않는다. 여러 단답형 문제는 만들지 않는다.

질문은 다음을 함께 확인할 수 있어야 한다.

- 핵심 개념의 역할
- 개념 사이의 실행 관계나 맥락
- 주어진 조건에서의 기술 선택
- 선택의 근거와 선택이 달라지는 조건

사용자는 자료를 보지 않고 다음 형식으로 답한다.

```text
답변 전 확신도: 1~5
내 설명: {핵심 흐름과 판단 근거}
확신이 없는 지점: {모르는 부분 또는 없음}
```

답변이 없으면 이해도와 메타인지를 추정하지 않고 `미확인`으로 기록한다.

## 이해 단계

```text
미확인      대화에서 다뤘지만 직접 확인하지 않음
재인 가능   설명을 보면 개념을 알아봄
설명 가능   자료 없이 개별 개념의 원리를 설명함
연결 가능   여러 개념의 관계와 전체 흐름을 설명함
판단 가능   제약에 맞는 선택과 근거, 선택이 바뀌는 조건을 설명함
```

단계는 당일 전체 역량이 아니라 확인 질문에서 관찰된 범위만 나타낸다.

## 출력 순서

```text
오늘의 한 줄 결론
→ 오늘 다룬 항목
→ 오늘의 중심 연결
→ 문제 ↔ 기술 판단
→ 아직 헷갈리는 지점
→ 메타인지 확인
→ 복습할 한 문장
```

## 출력 템플릿

````markdown
# 오늘의 학습 브리핑

> 기준일: YYYY-MM-DD

## 오늘의 한 줄 결론

{오늘 새롭게 형성된 이해나 가장 중요한 연결을 한 문장으로 작성한다. 단순한 주제 나열은 피한다.}

## 오늘 다룬 항목

- **중심:** `{키워드}` · `{키워드}` · `{키워드}`
- **함께 다룸:** `{키워드}` · `{키워드}`
- **보조:** `{키워드}` · `{키워드}`

대화나 코드에서 접한 범위를 보여주는 색인이다. 여기에 포함됐다는 이유만으로 이해했다고 표현하지 않는다. 빈 분류는 생략한다.

## 오늘의 중심 연결

```text
{개념 또는 실행 단계}
  → {개념 또는 실행 단계}
  → {개념 또는 실행 단계}
```

{각 개념을 따로 정의하지 않고, 누가·언제·왜 다음 단계로 연결되는지를 2~3개의 짧은 문단으로 설명한다. 하나가 빠지면 무엇이 달라지는지도 필요한 경우 포함한다.}

관련성이 약해 중심 흐름에 넣지 않은 개념은 `오늘 다룬 항목`에만 남긴다.

## 문제 ↔ 기술 판단

실제 코드나 당일 질문에 선택 문제가 있을 때만 작성하며, 하루에 한 사례만 다룬다.

### 문제

{해결하려는 문제와 현재 코드베이스의 조건을 짧게 설명한다. 규모, 일관성, 실패 처리, 운영 복잡도처럼 선택에 영향을 주는 조건만 남긴다.}

### 선택지와 기술

```text
선택지 A: {방법}
선택지 B: {방법}
```

### 현재 판단

{현재 조건에서 선택할 방법과 그 이유를 설명한다. 보편적인 정답처럼 표현하지 않는다.}

- **해결되는 것:** {이 선택이 직접 해결하는 문제}
- **해결되지 않는 것:** {별도 대책이 필요한 문제}
- **선택이 바뀌는 조건:** {규모, 요구사항, 장애 대응 방식 등이 어떻게 달라질 때 다른 선택이 적절해지는지}

## 아직 헷갈리는 지점

- **확인된 혼동:** {직접 답변에서 드러난 오해나 빠진 연결}
- **아직 미확인:** {대화에서는 다뤘지만 직접 설명하지 않은 부분}

근거가 없다면 혼동을 추정하지 않는다.

## 메타인지 확인

- **답변 전 확신도:** {1~5 또는 미응답}
- **관찰된 단계:** {미확인 / 재인 가능 / 설명 가능 / 연결 가능 / 판단 가능}
- **잘 설명한 부분:** {답변에서 확인된 내용}
- **확신과 실제 이해의 차이:** {과대평가, 과소평가, 대체로 일치 또는 미확인}
- **다음 확인 지점:** {현재 단계에서 한 단계 나아가기 위해 확인할 한 가지}

질문의 질, 탐구 의지, 끈기 같은 학습 태도를 이해도의 근거로 대신 사용하지 않는다.

## 복습할 한 문장

> {중심 연결과 판단 기준을 함께 떠올릴 수 있는 한 문장}
````

## 출력 전 점검

- 상단만 읽어도 오늘 다룬 범위와 핵심 연결을 알 수 있는가?
- 당일 학습 자료의 핵심 개념어가 `오늘 다룬 항목`에 모두 명시됐는가?
- 구체적인 개념어를 `아키텍처`, `MSA` 같은 상위 표현으로 뭉뚱그리지 않았는가?
- 본문의 흐름과 사례에 해당하는 정식 개념명이 직접 연결돼 있는가?
- 항목 목록이 본문에서 그대로 반복되지 않는가?
- 중심 연결이 실제 관련 있는 개념 3~6개로 구성됐는가?
- 기술과 문제가 양방향으로 연결됐는가?
- 현재 선택의 장점뿐 아니라 해결되지 않는 문제와 전환 조건도 드러나는가?
- 설명을 들은 것을 직접 이해한 것으로 표현하지 않았는가?
- 메타인지 판단이 사용자의 직접 답변을 근거로 하는가?
- 근거 없는 점수와 칭찬을 제거했는가?
- 전체를 5분 안에 읽을 수 있는가?
