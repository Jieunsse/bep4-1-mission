# 학습 개요와 현재 상태

지금까지 대화에서 다룬 개념과 현재 이해 상태를 기록한 문서다. 설명은 최신 이해를 기준으로 유지한다.

## 문서 길잡이

문서는 다음 순서로 읽는다.

1. `영역별 학습 현황`에서 전체 상태를 확인한다.
2. `메타인지 점검`에서 현재 학습 단계와 다음 목표를 확인한다.
3. 주제별 본문에서 질문, 현재 이해, 코드 흐름을 확인한다.
4. 마지막 `다음 학습 큐`에서 아직 연결하지 못한 주제를 고른다.

각 주제의 `다룬 질문`은 질문의 이력이고, `현재 이해한 내용`은 그 질문을 정리한 최신 답변이다. 같은 내용을 새 질문으로 반복해서 쌓지 않는다.

## 문서 관리 원칙

- 새로운 기술 질문은 관련 주제 아래에 추가한다.
- 기존 내용과 중복되는 질문은 새 항목을 만들지 않고 기존 설명을 보강한다.
- 꼬리질문은 앞선 개념과의 관계가 드러나도록 연결해서 기록한다.
- 이해가 바뀌거나 정정된 내용은 이전 설명을 그대로 쌓지 않고 최신 이해로 갱신한다.
- 질문뿐 아니라 `현재 이해한 내용`, `헷갈리는 부분`, `앞으로 확인할 질문`도 함께 최신화한다.

## 설명 방식 선호

- 어려운 기술 개념은 먼저 가장 쉬운 비유나 한 줄 비교로 핵심을 잡는다.
- 그다음 실제 코드 흐름을 설명한다.
- 마지막으로 어노테이션, 프레임워크 내부 동작, 예외와 한계 같은 세부사항으로 들어간다.
- 설명 순서는 기본적으로 다음을 따른다.

```text
쉬운 비유
  → 한 줄 핵심
      → 현재 코드 예시
          → 내부 동작과 주의점
```

- 사용자가 “쉽게”, “간단하게”, “직관적으로” 설명해달라고 하면 비유와 비교를 먼저 제시한다.

## 영역별 학습 현황

현재까지의 질문을 기술 영역별로 분류한 표다. `미확인`은 모른다는 뜻이 아니라, 아직 대화에서 확인하지 않은 영역이라는 뜻이다.

| 영역 | 현재 기록된 주제 | 상태 |
| --- | --- | --- |
| Java 문법·언어 | 제네릭, 다이아몬드 연산자, 익명 클래스, 향상된 for문, 메서드 체이닝, 생성자 | 이해 진행 중 |
| Spring Core | Bean, Proxy, `@Lazy`, `@Transactional`, 이벤트 리스너, 설정 파일 import와 환경변수 | 핵심 개념 이해 진행 중 |
| Spring 아키텍처 | Facade, UseCase, Support, Repository, 오케스트레이션, 코레오그래피, 사가 패턴, 이벤트 기반 흐름, 모노프로젝트의 MSA 지향 모듈 분리 | 구조 이해 진행 중 |
| Spring Data JPA·DB | Repository 프록시, 메서드 이름 기반 조회, `Optional`, 트랜잭션, `readOnly`, `AFTER_COMMIT`, `REQUIRES_NEW` | 일부 이해, 심화 필요 |
| HTTP·API | GET 요청, URI·URL, `RestClient`, 응답 처리 | 기본 흐름 이해 |
| 네트워크 | 현재 대화에서 별도 질문 없음 | 미확인 |
| JSON·직렬화 | Jackson, DTO 변환, `@JsonCreator`, `ParameterizedTypeReference` | 변환 흐름 이해 진행 중 |
| Lombok | `@Slf4j`, 생성자 자동 생성 | 기본 이해 |
| CS·알고리즘 | 현재 대화에서 별도 질문 없음 | 미확인 |
| 테스트·빌드 | 현재 대화에서 별도 개념 질문 없음 | 미확인 |

## 메타인지 점검

### 현재 학습 단계

현재는 **Java 기초 문법을 다시 다지면서 Spring 애플리케이션의 실행 흐름을 연결하는 단계**다. 단순히 어노테이션의 뜻을 외우기보다 다음 질문을 통해 실제 호출 흐름을 확인하는 학습 패턴을 보이고 있다.

```text
누가 호출하는가?
어떤 객체가 전달되는가?
다음에는 누가 실행되는가?
DB 작업은 어디서 일어나는가?
Spring은 중간에 무엇을 자동 처리하는가?
```

### 잘 이해하고 있는 부분

- Facade를 앱의 진입점으로 두고, 무거운 기능은 UseCase, 가벼운 기능은 Support로 위임하는 책임 분리를 설명할 수 있다.
- 이벤트를 DB 조회가 아니라 후속 작업을 알리는 메시지로 이해하고 있다.
- `EventPublisher → Spring 이벤트 시스템 → EventListener`의 전달 구조를 이해하고 있다.
- 회원가입부터 회원 복제, 지갑 생성까지 이벤트가 연쇄되는 흐름을 추적할 수 있다.
- Proxy를 공통 기능을 처리하는 대리 객체로 설명할 수 있다.
- RestClient, URI, 응답 JSON, DTO 변환의 큰 흐름을 설명할 수 있다.
- 모듈 분리의 기준을 패키지 분리가 아니라 다른 모듈 클래스의 직접 `import` 제거로 설명할 수 있다.
- 모듈 간 결합을 끊기 위해 사건은 이벤트, 값은 API, 필요한 Entity는 복제 테이블로 전달하는 구분을 설명할 수 있다.

### 아직 연결을 더 강화해야 하는 부분

- Java 제네릭, 타입 추론, 익명 클래스가 런타임 타입 정보와 어떻게 연결되는지
- `@Transactional` 프록시가 실제로 적용되는 호출 경계와 `this` 호출의 차이
- JPA의 영속성 컨텍스트, Entity 생명주기, 지연 로딩, 트랜잭션 경계
- `AFTER_COMMIT` 이벤트 실패 시 처리와 `REQUIRES_NEW`의 실제 동작
- Spring Event에서 Kafka로 전환할 때의 consumer group, offset, 재처리와 멱등성
- 복제 테이블의 동기화 지연·실패와 데이터 정합성
- Jackson의 직렬화·역직렬화와 `ParameterizedTypeReference`가 필요한 이유

### 아직 확인하지 않은 영역

- 네트워크의 TCP/IP, DNS, 소켓, HTTP 동작 원리
- 자료구조와 알고리즘, 시간·공간 복잡도
- 테스트 전략과 빌드 도구의 동작 원리

### 학습 패턴

- 강점: 코드를 보면서 호출 관계와 데이터 이동을 끝까지 추적한다.
- 강점: 모르는 용어를 그냥 넘기지 않고 어원과 역할까지 확인한다.
- 현재 혼동 지점: Java 문법, Spring 자동 처리, 애플리케이션 비즈니스 로직이 한 코드 안에서 동시에 보일 때 경계를 구분하는 데 시간이 필요하다.
- 다음 목표: 코드 한 줄을 볼 때 `내가 작성한 코드`, `Spring이 내부에서 대신 하는 일`, `라이브러리가 변환하는 일`을 분리해서 설명하는 것.

### 영역 분류 기준

- Java 문법: 언어 자체의 문법과 객체 생성 방식
- Spring Core: Bean 생명주기, 프록시, AOP, 트랜잭션, 이벤트 시스템
- Spring 아키텍처: 프로젝트 내부 계층과 책임 분리 방식
- Spring Data JPA·DB: Repository, 영속성, 트랜잭션, 데이터베이스 동작
- HTTP·API: 요청·응답, URL·URI, REST Client
- 네트워크: TCP/IP, DNS, HTTP 통신 구조, 소켓, 네트워크 보안 등
- JSON·직렬화: JSON과 Java 객체 사이의 변환
- Lombok: 반복 코드를 줄이는 컴파일 타임 어노테이션
- CS·알고리즘: 자료구조, 시간·공간 복잡도, 운영체제, 네트워크 등

## 전체 이해 구조

```text
API 요청
  ↓
Controller
  ↓
Facade
  ├─ 조회 → Support → Repository
  └─ 업무 처리 → UseCase → Repository
                         ↓
                    필요할 때 EventPublisher
                         ↓
                    Spring 이벤트 시스템
                         ↓
                    EventListener
                         ↓
                    Facade → UseCase
```

## 다음 학습 큐

- `@Transactional` 프록시는 실제로 어떤 시점에 생성되는가?
- `AFTER_COMMIT` 이벤트에서 `REQUIRES_NEW`가 필요한 이유는 무엇인가?
- Java 제네릭 타입 소거 때문에 `ParameterizedTypeReference`가 필요한 경우는 언제인가?
- `body(PostDto.class)`와 `body(new ParameterizedTypeReference<PostDto>() {})`의 차이는 무엇인가?
- 이벤트 처리 실패 시 재시도나 보상 처리는 어떻게 설계하는가?
- 현재 이벤트 흐름에서 중복 이벤트나 중복 지갑 생성을 어떻게 방지하는가?
